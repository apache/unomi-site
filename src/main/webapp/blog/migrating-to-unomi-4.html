Upgrades

Migrating to Unomi 4

The usual upgrade is Unomi 3.x to 4.0. Unomi 2.x is a longer path that first takes the Unomi 3 platform steps.

The API stays familiar

Unomi 4 does not rip out the 2.x REST map. In the OpenAPI specs tracked for testing, every one of the 119 Unomi 2.x paths is still present in 4.0 — new capabilities (tenants, tasks, …) are additive.

Native Unomi 4.0 authentication expects tenant API keys. For a calm cutover, enable single-tenant compatibility mode so Unomi 2.x and 3.x clients keep working while you migrate traffic, then disable the mode when ready.

Migration paths

  1. From Unomi 3.0.x or 3.1.0 — this is the upgrade most installs take. Java 17, Karaf 4.4.8, Elasticsearch 9.1.3, persistence clustering, and health checks are already in place. Upgrading requires a data migration: stop the 3.x cluster, install 4.0, set UNOMI_ROOT_PASSWORD and UNOMI_HEALTHCHECK_PASSWORD (4.0 has no default password), and run unomi:migrate with the version you are coming from (for example unomi:migrate 3.0.0) from the Karaf shell. Existing data lands in the tenant you name at the prompt (default unless you choose another), and the generated API keys are written under data/migration/secrets/. Query builder ids were renamed in 4.0: the migration rewrites stored ones, and legacy ids in your plugin definitions still work but log a warning, so move them to the new ids. Elasticsearch 9.4.3 is the tested and recommended version (the supported range still starts at 9.0.3), or adopt OpenSearch 3.7.0. Then move clients to tenant API keys and the Unomi 4 APIs.
  2. From Unomi 2.x (including 2.7) — do the Unomi 3 platform steps as well: Java 17+ (Java 11 will not start 4.0), Karaf 4.4.12, and Elasticsearch 7 (2.7.0 pins 7.4.2) → 9.4.3 or OpenSearch 3.7.0, then the same data migration, QueryBuilder ID renames, tenant API keys and new APIs.
  3. Single-tenant compatibility mode — phased transition for Unomi 2.x and 3.x clients
  4. Optional Elasticsearch → OpenSearch migration

Follow the official manual chapters rather than duplicating long procedures here, starting with the 3.0 to 4.0 migration guide and single-tenant compatibility mode.
