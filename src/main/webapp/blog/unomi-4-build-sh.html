Unomi 4 · Developer experience

One entry point: build.sh

Preflight, build, test, and deploy — the same script locally and on GitHub Actions.

{% if page.date %}

Published {{ page.date | date: "%B %d, %Y at %H:%M UTC" }}

{% endif %}

Before Unomi 4, contributors juggled several ad-hoc scripts (buildAndRun.sh, compileDeploy.sh, and friends). UNOMI-887 / #737 folded those workflows into a single ./build.sh at the repository root — with clearer errors, colorized output, and flags that match how people actually work.

What it replaced

Legacy one-off scripts for “build and run,” “build without tests,” packaging, and deploy were removed in favor of one maintained entry point. The PowerShell twin build.ps1 covers most of the same flags for Windows contributors (it has no equivalent of --no-clean or --no-javadoc yet).

What you get

  • Preflight — Java, Maven, GraphViz; memory/disk heuristics; ports for debug sessions; fail early with readable messages
  • Build flexibility — skip tests, OpenSearch vs Elasticsearch, named distributions, offline / Maven debug, optional Javadoc gate
  • Integration tests — --integration-tests, --single-test, IT debug/suspend, keep container, stream search logs when needed, memory sampler
  • Run & deploy — --deploy --karaf-home, Karaf debug ports, --auto-start to start Unomi against Elasticsearch or OpenSearch once Karaf is up, --no-karaf for package-only builds
  • CI mode — --ci skips the script’s prompts, hides Maven transfer progress (-ntp), turns on the Javadoc gate, and does not start Karaf; GitHub Actions calls the same script as you do locally (#764)
  • UX details — section headers, traps with line/context on failure, NO_COLOR respected, optional --log-file tee

Try it

./build.sh --help

# Build only
./build.sh --no-karaf

# Default: build, then unpack and start Karaf.
# Karaf refuses to start unless both passwords are set.
export UNOMI_ROOT_PASSWORD='choose-a-strong-password'
export UNOMI_HEALTHCHECK_PASSWORD='choose-a-strong-health-password'
./build.sh

# Match GitHub Actions shape
./build.sh --ci

# Full IT matrix flavors (--no-karaf: do not start Karaf after the tests)
./build.sh --integration-tests --no-karaf
# OpenSearch runs need the admin password exported first.
# Use a separate shell: with it set, the Elasticsearch run refuses to start.
export UNOMI_OPENSEARCH_PASSWORD='MyStrongPassw0rd!'
./build.sh --integration-tests --use-opensearch --no-karaf

# One flaky test under a debugger
./build.sh --integration-tests --no-karaf \
  --single-test org.apache.unomi.itests.graphql.GraphQLEventIT \
  --it-debug --it-debug-suspend

# Deploy KAR into an existing Karaf (without starting the freshly built one)
./build.sh --deploy --karaf-home ~/apache-karaf --no-karaf

Why it matters

Contributor friction kills review velocity. One documented command that validates the environment, builds the right distribution, and runs the same gates as CI means less “works on my machine” archaeology — and pairs with the clearer IT console and manual investments in Unomi 4.
